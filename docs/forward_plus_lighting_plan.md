# Forward+ / Clustered Forward PBR Lighting

## Context

Toast Engine's mesh shader (`mesh.slang`, duplicated at root and `editor/`) currently does no real lighting: it samples albedo and multiplies by a flat push-constant color. Five `Light` node classes (`Light`, `PointLight`, `DirectionalLight`, `Spotlight`, `AmbientLight`) already exist in `engine/src/toast/world/` and are fully reflected/creatable/serializable in the editor, but are header-only with zero behavior — they don't register with the engine, and nothing in the renderer consumes them. The `Material` asset has `albedo_map`/`normal_map`/`color` but no metallic/roughness, and `normal_map` is resolved into a working `AssetHandle<Texture>` that nothing downstream ever samples.

The goal: give materials a simple metallic/roughness PBR model (scalars only, no texture maps for those two), wire the existing Light nodes up to actually affect rendering, and do the lighting as **Forward+/clustered forward** (not deferred) — which requires adding compute shader support to the Vulkan renderer, since none exists today (no compute command pool/buffer, no `vkCmdDispatch` anywhere, though the compute queue family, `VulkanPipeline`'s compute-pipeline path, and a storage-buffer-provisioned descriptor pool already exist unused).

This was scoped via deep research (three parallel Explore passes over the lighting/node system, the renderer's compute-readiness, and the shader/material/schema pipeline) followed by a Plan-agent adversarial review specifically targeting the new compute↔graphics synchronization design. The review caught one significant bug in the original draft (see "GPU buffer lifetime" below) and several smaller correctness gaps, all folded into this plan.

## Architecture decisions

**Light node type tagging**: `Light` gets `init()/end()/destroy()` (once, in the base class) mirroring `MeshNode`'s proven registration pattern. **Correction from the 2026-07-18 refresh**: the original draft mischaracterized where that pattern actually lives — it is *not* `Engine::registerMeshNodeProxy`. The real chain is: `MeshNode::init()` (`mesh_node.cpp:7-19`) calls the free function `renderer::registerMeshNodeProxy(this)`, which is a thin inline forwarder (`vulkan_renderer.hpp:354-360`) straight to `VulkanRenderer::instance->registerMeshNodeProxy(node)` — a member function of `VulkanRenderer` itself, which owns the mutex-guarded vector (`m_mesh_proxy_mutex`/`m_mesh_proxy_nodes`, private members of `VulkanRenderer`) and later snapshots it directly inside its own `tick()`. `Engine`/`EnginePimpl` play no role at all in mesh-proxy registration today. Lights should mirror this *exactly* — `renderer::registerLightNodeProxy(this)`/`unregisterLightNodeProxy(this)` free functions forwarding into new `VulkanRenderer` methods, with `VulkanRenderer` owning the light-proxy vector alongside its existing mesh-proxy one — not a new registry hung off `Engine`/`EnginePimpl`, which would be a real architectural deviation dressed up as "mirroring" it. Verified empirically that the C++ runtime's `Node::callTick` (`node.cpp:251-316`) walks the full `NodeInfo::base_type` chain and invokes each ancestor's own hooks against the real derived `this` — so subclasses need zero boilerplate for this to fire. Each subclass tags its concrete type via a plain non-reflected `LightType m_light_type` field set in its own constructor body (`PointLight() { setLightType(LightType::Point); }`) — not RTTI (avoids per-frame `dynamic_cast` cost), not a pure-virtual (would make `Light` abstract and break the codegen'd `light_construct()` factory, which unconditionally does `new toast::Light()`). Verified safe against prefab deserialization: `applyFields()` only ever touches `[[Reflect]]`-tagged fields, and `m_light_type` deliberately isn't one, so nothing can clobber the constructor-set value.

**Global vs. clustered lights**: `AmbientLight` and `DirectionalLight` are unbounded/unculled — fold them directly into the existing `FrameUBO`/`CameraUBO` (ambient pre-summed to one CPU-side value across all `AmbientLight` nodes since it has no position/direction; directional lights as a small fixed-size array, cap 4) rather than inventing a new UBO. This reuses the existing per-frame update path (`updateFrameResources()`) and existing set0 binding — no new descriptor binding needed for these. Only `PointLight`/`Spotlight` go through the new clustered system.

**Clustering**: fixed 16×9×24 (=3456) view-space cluster grid, logarithmic Z-slicing (standard Doom2016/Olsson-Assarsson formula), rebuilt every frame for simplicity (3456-thread dispatch is trivial; only-rebuild-on-projection-change is a later optimization, not needed now). Two compute dispatches back-to-back in one command buffer with a compute→compute buffer barrier between them: `clusterBuildMain` (writes per-cluster view-space AABBs) then `lightCullMain` (sphere-vs-AABB tests each cluster against all lights, writes a **fixed-stride-per-cluster** light index list — `kClusterCount * kMaxLightsPerCluster` slots — instead of a global-atomic-offset scheme, trading trivial VRAM for eliminating an entire class of "did the atomic counter get reset before this frame" bugs). Both entry points share one `.slang` file, one pipeline layout, one descriptor set — no reason to split them.

**GPU buffer lifetime (critical correction from review)**: all five buffers (`ClusterParams` UBO, `Lights` SSBO, `ClusterAABB` SSBO, `ClusterLightGrid` SSBO, `LightIndexList` SSBO) need **`kFramesInFlight` independent instances each**, not one shared instance. With 3 frames in flight, frame N+1's compute dispatch can legitimately start on the GPU before frame N's fragment shader has finished reading these buffers — nothing today orders slot N against slot N+1 except each slot's own fence, 3 iterations apart. A single shared instance would be a real cross-queue write/read race. Multi-instancing them (mirroring how `m_frame_ubo_res` already works) means the *existing* `frame.in_flight` fence wait already covers reuse safety for free, and descriptor sets referencing them can be written **once at construction**, never rewritten per-frame.

**Descriptor set sharing**: rather than trying to share one literal `VkDescriptorSet` between the compute pipeline (which writes the cluster/light buffers) and `MeshPass`'s graphics pipeline (which reads them in the fragment shader) — which would require two independently-built `HardcodedPipelineLayouts` table entries to produce byte-for-byte-compatible `VkDescriptorSetLayout`s, an extra cross-file consistency contract nothing here checks — allocate **two separate descriptor sets pointing at the same underlying buffers**: one owned by `ClusterLightingPass` for its own compute dispatches, one owned by `MeshPass` itself (a new set2, sourcing raw buffer handles from a `const ClusterLightingPass&` passed into `MeshPass`'s constructor). This means `ClusterLightingPass` must be constructed before `MeshPass` in `engine.cpp` (both `createSDLWindow()` and `createAvaloniaWindow()` — the editor viewport also runs a `MeshPass` and needs this too). Confirmed correct: descriptor sets have no bearing on synchronization scope (that's purely the buffer + access/stage flags), so this costs a handful of extra `vkUpdateDescriptorSets` calls and nothing else.

**Compute↔graphics synchronization**: new compute command pool (built on the compute queue family, which is already guaranteed distinct from graphics by device selection — replaces the existing `// TODO: Compute Command Pool` marker), one compute command buffer + one binary semaphore (`compute_to_graphics`) + one dedicated fence (`compute_in_flight`, defense-in-depth per the review) per `FrameContext` slot (sized off `kFramesInFlight`, confirmed the correct constant — `kRenderFrames` governs the separate CPU-side main-thread/render-thread handoff ring, not GPU frame resources). Every frame, **unconditionally** (even if nothing changed): reset/record/submit the compute command buffer signaling `compute_to_graphics`; the graphics submit's wait-semaphore array is unconditionally extended to also wait on `compute_to_graphics` at `eFragmentShader` stage. This must never become conditional on "did compute have work to do" — an empty dispatch submission is cheap and keeps the invariant simple; the review's main warning was that this exact kind of shortcut (the existing dead/commented-out `transfer_finished` semaphore) is how this class of bug entered the codebase before. Classic `vk::SubmitInfo`/`cmd.pipelineBarrier` (sync1) throughout — `synchronization2` is enabled as a device feature but unused anywhere in the codebase today, and buys nothing here. The `ClusterAABB`/`ClusterLightGrid`/`LightIndexList`/`Lights`/`ClusterParams` buffers use `VK_SHARING_MODE_CONCURRENT` across graphics+compute families (mirroring `vulkan_mesh.cpp`'s existing concurrent vertex/index buffers) so the semaphore's built-in memory-availability/visibility guarantee is sufficient cross-queue with no extra barrier needed; the intra-compute-queue `clusterBuild → lightCull` dependency on `ClusterAABB` needs its own explicit `vk::PipelineStageFlagBits::eComputeShader → eComputeShader` memory barrier (write→read).

**Shading space**: keep world-space BRDF math (matches the shader's existing convention — `worldNormal`, `CameraUBO.position`). Each `GpuLight` carries both a world-space position (for shading) and a view-space position (culling test only); directional lights need no space conversion at all since they skip clustering entirely. `VSOutput` gains a world-space fragment position (doesn't exist today — the current fake-lighting shader never needed one) and an interpolated view-space Z (computed in the vertex shader via the already-available `gCamera.view`, used for the cluster Z-slice lookup — simpler and more robust than reversing nonlinear depth back out of `SV_Position.z`).

## Data layouts (implementation may adjust exact packing; shape shown for concreteness)

```cpp
// Extends existing FrameUBO/CameraUBO (set0, binding0) — ambient/directional are global, not clustered
struct FrameUBO {
    glm::mat4 view, projection, view_projection;
    glm::vec3 camera_position;
    float time;
    // NEW:
    glm::vec4 ambient_color_intensity;   // pre-summed across all AmbientLight nodes on CPU
    uint32_t directional_light_count;
    glm::vec3 _pad0;
    struct { glm::vec4 direction; glm::vec4 color_intensity; } directional_lights[4]; // world-space
};

// New "Lights" SSBO entry (point + spot only)
struct GpuLight {
    glm::vec4 world_pos_range;   // xyz world-space position, w = attenuation range (sphere radius, falloff distance)
    glm::vec4 view_pos_type;     // xyz view-space position (culling only), w = type (0=point,1=spot)
    glm::vec4 color_intensity;   // rgb color, a intensity
    glm::vec4 direction_pad;     // xyz world-space direction (spot only)
    glm::vec4 cone_angles;       // x = cos(outer), y = cos(inner)
};

// New ClusterParams UBO — read by both compute dispatches and the fragment shader
struct ClusterParams {
    glm::mat4 inverse_projection;
    glm::uvec4 cluster_dims;          // x,y,z dims, w = kMaxLightsPerCluster
    glm::vec4 screen_size_near_far;   // x,y screen dims, z near, w far
    uint32_t light_count;
    glm::vec3 _pad0;
};

// ClusterAABB SSBO (compute-internal only, not exposed to MeshPass): { vec4 min_point; vec4 max_point; } * kClusterCount
// ClusterLightGrid SSBO (written by lightCull, read by fragment): uint count[kClusterCount]
// LightIndexList SSBO (written by lightCull, read by fragment): uint indices[kClusterCount * kMaxLightsPerCluster]
```

Constants (new small header, e.g. `clustered_lighting_constants.hpp`): `kClusterDimX=16, kClusterDimY=9, kClusterDimZ=24, kClusterCount=3456, kMaxLightsPerCluster=128, kMaxDirectionalLights=4, kMaxLights=512` (preallocated capacity for the `Lights` SSBO).

**Fixed-stride light list correctness requirement**: `lightCullMain` must run one-thread-per-cluster (looping serially over all lights) — not one-thread-per-light scattering into clusters, which would need atomics and reintroduce the reset problem this design avoids. Must double-clamp: guard the *write* (`if (count < kMaxLightsPerCluster) { list[...] = i; }`) so an overflowing cluster can't corrupt its neighbor's slice, AND clamp the *stored count* (`min(count, kMaxLightsPerCluster)`) so the fragment shader can't read past what was written. Also needs an explicit `if (clusterIndex >= kClusterCount) return;` bounds check since dispatch sizes round up to whole workgroups.

## Staged implementation order

Each stage is independently buildable and verifiable before the next begins — this is genuinely new Vulkan sync code, and stages are ordered to isolate "is it my sync code or my shading math" when something looks wrong.

### Stage 1 — Material PBR scalars + normal mapping (no lighting yet)
Wire `metallic`/`roughness` through end-to-end and get normal mapping visibly working, still using the existing fake half-lambert term — isolates data-plumbing bugs from lighting-math bugs before either compute or real BRDF code exists. Sequence the mechanical part (schema→accessor→push-constant→shader, verify by outputting `metallic` as grayscale) before the TBN math.

- `engine/assets/schemas/material.schema.json` — add `metallic`/`roughness` (`"type":"number","x-toast-type":"float"`, range `[0,1]`, defaults 0.0/0.5). Editor UI needs no C# changes (generic schema-reflective inspector already renders `x-toast-type:"float"` as a bound `DragFloatBox`).
- `engine/src/toast/assets/material.hpp` / `.cpp` — `metallic()`/`roughness()` accessors, same defensive int-or-float read pattern as the existing `readColor()`.
- `engine/src/toast/renderer/passes/mesh_pass.hpp` / `.cpp` (file is snake_case under `passes/`; class is still `MeshPass`) — `DrawPushConstants` gains `glm::vec4 pbr_params` (x=metallic, y=roughness), pushing 80→96 bytes (well under the guaranteed 128-byte minimum). `createDefaultMaterialResources()` adds a default flat-normal (0.5,0.5,1.0) 1×1 texture+sampler, written to a new binding1 in both the default material set and every per-material set (using `material.normalMap()` if present+ready, else the default) — mirrors the existing albedo/white-texture fallback exactly.
- `engine/src/toast/renderer/hardcoded_pipeline_layouts.cpp` (no `core/` subdirectory exists — this file is directly under `renderer/`) — `"mesh"` key: push-constant size 80→96; set1 gains binding1 (combined-image-sampler, fragment).
- `mesh.slang` **and** `editor/mesh.slang` (keep byte-identical, diff after this stage) — forward `tangent` to `VSOutput` (currently read then dropped), add world-space fragment position and view-space Z to `VSOutput`, Gram-Schmidt TBN construction, second sampler binding, `PushConstants` struct match.
- **Verify**: visually confirm normal maps affect apparent shading correctly (not washed out — flag and check texture cook colorspace: normal maps must be UNORM, not sRGB; nothing has ever sampled `normalMap()` before so this has never been exercised).

### Stage 2 — Light node lifecycle + VulkanRenderer collection
Pure repetition of the already-proven `MeshNode` registration pattern — low risk, no new architecture. Verify via logging/debugger only; no GPU consumption yet.

- `engine/src/toast/world/light.hpp` — `LightType` enum, non-reflected `m_light_type` + `setLightType()`/`lightType()` getter, declare `init()/end()/destroy()`, `bool m_registered_proxy`.
- `engine/src/toast/world/light.cpp` — new file, mirrors `mesh_node.cpp` exactly (`renderer::registerLightNodeProxy(this)` in `init()`, `unregisterLightNodeProxy(this)` in `end()`/`destroy()` — not `Engine::get()->...`; see the Stage 2 renderer bullet below for where these free functions actually forward to).
- `engine/src/toast/world/point_light.hpp` — constructor sets `LightType::Point`; add `[[Reflect, Unit("m"), Range(0,1000)]] float m_attenuation = 10.0f;` (reusing `Spotlight`'s existing field name for this concept, for naming consistency within the Light family — doubles as shading falloff distance and culling-sphere radius).
- `engine/src/toast/world/directional_light.hpp` — constructor sets `LightType::Directional`.
- `engine/src/toast/world/spotlight.hpp` — constructor sets `LightType::Spot` (fields already exist: `m_inner_radius`, `m_outer_radius`, `m_attenuation`).
- `engine/src/toast/world/ambient_light.hpp` — constructor sets `LightType::Ambient`.
- `engine/src/toast/renderer/vulkan_renderer.hpp` / `.cpp` (no `core/` subdirectory — see correction above; **not** `engine.hpp`/`.cpp`, which owns none of the mesh-proxy pattern this mirrors) — `registerLightNodeProxy`/`unregisterLightNodeProxy` member functions on `VulkanRenderer` itself, alongside the existing `registerMeshNodeProxy`/`unregisterMeshNodeProxy`, plus matching `renderer::registerLightNodeProxy(toast::Light*)`/`unregisterLightNodeProxy(...)` free-function inline forwarders (mirroring the existing mesh ones exactly — this is what `light.cpp` above actually calls); `VulkanRenderer` gains its own `m_light_proxy_mutex`/`m_light_proxy_nodes` (private members, same shape as the existing `m_mesh_proxy_mutex`/`m_mesh_proxy_nodes`); `FrameUBO` extended per the layout above; `RenderFrame` gains a `lights` vector (inert until stage 3b). Extend `VulkanRenderer::tick()`'s existing mesh-proxy-snapshot section (`vulkan_renderer.cpp`, right where `m_mesh_proxy_nodes` is already locked/copied and `FrameUBO` is already built) to also snapshot `m_light_proxy_nodes` and populate the extended `FrameUBO` fields (ambient pre-summed, directional array) plus `RenderFrame.lights` (raw `GpuLight`-shaped data — world+view position, computed using the `m_camera` view matrix already resolved at that point in `tick()`) — this is the natural site since it's already where mesh collection + camera-matrix resolution + `FrameUBO` construction all happen together; no new plumbing through `Engine::tick()` needed.

### Stage 3a — Compute sync skeleton (no real shaders)
The highest-risk new code in this plan — validate the submit/wait/fence skeleton in isolation with an empty dispatch before any real compute logic sits on top and makes a failure ambiguous.

- `engine/src/toast/renderer/compute_pass_base.hpp` (no `core/` subdirectory exists — sibling of the existing `render_pass_base.hpp`) — new; `IComputePass` symmetric to `IRenderPass`: `update(uint32_t frame_index, float dt)` + `dispatch(vk::CommandBuffer cmd, uint32_t frame_index)` (no `imageIndex` — compute isn't tied to a swapchain image; no `RenderFrame&` param — implementors fetch it via `VulkanRenderer::instance->renderingFrame()` like `MeshPass`/`DebugPass` already do).
- `engine/src/toast/renderer/vulkan_renderer.hpp` (no `core/` subdirectory — see path correction above) — `FrameContext` gains `compute_command_buffer`, `compute_to_graphics` (binary semaphore), `compute_in_flight` (dedicated fence — defense in depth so "safe to reset the compute command buffer" is a direct local fact, not a multi-hop inference through the graphics submit's semaphore behavior); `m_compute_passes` vector + `addComputePass()`.
- `engine/src/toast/renderer/vulkan_renderer.cpp` — `createComputeCommandPool()` (replaces the `// TODO: Compute Command Pool` marker, still present verbatim at `vulkan_renderer.cpp:107`) on `VulkanCore::getComputeQueueFamilyIndex()` (already exists, `vulkan_core.hpp:82`; `VulkanCore` also already has a working `m_compute_queue`/`getComputeQueue()` — device selection already guarantees this family is distinct from graphics); allocate the new per-slot objects; wire into `drawFrame()`: wait `compute_in_flight` alongside the existing `frame.in_flight` wait at the top; **unconditionally** reset/record(empty for now)/submit the compute command buffer signaling `compute_to_graphics` and `compute_in_flight`; extend the existing graphics submit's wait-semaphore/wait-stage arrays to always include `compute_to_graphics` at `eFragmentShader`. Structure this as a single non-conditional code path with a comment on why it must never become conditional.
- **Verify**: extended soak run with validation layers on, ideally with synchronization validation enabled (`VK_LAYER_ENABLES=VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT`) — confirm no validation errors, no hangs, no leaks across thousands of frames, before writing a single real compute shader.

### Stage 3b — ClusterLightingPass + real compute shaders
- `engine/src/toast/renderer/clustered_lighting_constants.hpp` (no `core/` subdirectory) — new; the constants listed above.
- `engine/src/toast/renderer/passes/cluster_lighting_pass.hpp` / `.cpp` (snake_case file under `passes/`, matching `mesh_pass.hpp`/`debug_pass.hpp`; class name stays `ClusterLightingPass`) — new; owns `kFramesInFlight` instances each of `ClusterParams`/`Lights`/`ClusterAABB`/`ClusterLightGrid`/`LightIndexList` (concurrent sharing on the four graphics-visible ones, exclusive fine for `ClusterAABB`); one shared pipeline layout + descriptor set (own copy, for compute); two `VulkanPipeline` instances (`clusterBuildMain`, `lightCullMain`) sharing that one layout; `update()` uploads `ClusterParams`+`Lights` from the current `RenderFrame`; `dispatch()` records both compute passes with the `eComputeShader→eComputeShader` barrier between them (plus the `clusterIndex >= kClusterCount` bounds check and the double-clamp on light count, both inside `lightCullMain`); exposes per-slot raw buffer-handle getters for `MeshPass` (everything except `ClusterAABB`, which stays compute-internal).
- `engine/src/toast/renderer/hardcoded_pipeline_layouts.cpp` — new `"cluster_lighting_compute"` key: one set, 5 bindings (`ClusterParams` UBO, `Lights`/`ClusterAABB`/`ClusterLightGrid`/`LightIndexList` SSBOs), all `stageFlags=eCompute`.
- `cluster_lighting.slang` **and** `editor/cluster_lighting.slang` — new; both entry points, shared resource declarations, one file.
- `engine/src/toast/engine.cpp` — construct `ClusterLightingPass` **before** `MeshPass` in both `createSDLWindow()` and `createAvaloniaWindow()` (both the player and editor viewport run a `MeshPass`); register via `addComputePass()`.
- **Verify**: RenderDoc capture (the engine already exposes `VulkanCore::getRenderDocAPI()`), inspect `ClusterAABB`/`ClusterLightGrid`/`LightIndexList` buffer contents directly. Place one test point light at a known position, hand-compute which cluster indices its sphere should overlap given the log-slice formula, confirm matching `ClusterLightGrid`/`LightIndexList` entries and zero counts in distant clusters — entirely isolated from `mesh.slang`/`MeshPass`, so a bug here can't be confused with a shading bug.

### Stage 4 — MeshPass integration + full PBR fragment shader
- `engine/src/toast/renderer/hardcoded_pipeline_layouts.cpp` — `"mesh"` key gains set2 (4 bindings — `ClusterParams`, `Lights`, `ClusterLightGrid`, `LightIndexList` — all `stageFlags=eFragment`).
- `engine/src/toast/renderer/passes/mesh_pass.hpp` / `.cpp` — constructor takes `const ClusterLightingPass&` (used transiently at construction, not stored); allocates+writes `kFramesInFlight` set2 descriptor sets **once** at construction (buffer addresses are stable for the pass's lifetime, same reasoning as set0); `record()` binds set2 alongside set0.
- `mesh.slang` / `editor/mesh.slang` (diff-check both again after this stage) — cluster index from the interpolated view-space Z (log-slice inverse) + screen-space XY tile; loop `ClusterLightGrid`/`LightIndexList` for point/spot contributions plus the small fixed directional array from `CameraUBO`; GGX normal distribution + Smith/Schlick-GGX geometry + Schlick Fresnel BRDF, energy-conserving diffuse/specular split (F0 lerp 0.04→albedo by metallic, diffuse weighted by 1-metallic); inverse-square falloff smoothly clamped at each light's range, spot cone smoothstep between inner/outer angle; flat ambient term (`ambient.rgb * ambient.a * albedo * (1-metallic)`).
- **Verify**: visual end-to-end test in a scene with a few point lights + one directional + ambient, metallic/roughness varying across test materials.

### Stage 5 — Polish
- `mesh.slang` / `editor/mesh.slang` — basic Reinhard tonemap + gamma 2.2 (the engine has zero tonemapping today; raw PBR output will look blown out without at least this).
- Final diff of every touched `.slang` pair (root vs. `editor/`), full `ctest` regression run, extended validation-layer soak test.

## Verification (throughout, not just at the end)

- Build via CLAUDE.md's documented commands (`cmake --build ./build/Debug` on Windows).
- Run `ctest --test-dir build/Debug -C Debug` after each stage — regression check, though existing tests are unlikely to touch this code directly.
- Use the `run` skill to launch the editor/player and visually confirm each stage's specific verification point (listed per stage above) before moving on.
- Enable Vulkan validation layers (already plumbed via `VulkanCore::validationEnabled()`) throughout, especially synchronization validation during stage 3a.
- Use RenderDoc (`VulkanCore::getRenderDocAPI()`) for stage 3b's buffer-content verification and any later visual debugging.
- Diff root vs. `editor/` copies of every touched `.slang` file after stages 1, 3b, and 4 specifically (not deferred to the end) — this hand-maintained duplication is a pre-existing hazard, not something this plan fixes, so it needs active vigilance at every stage that touches a shader.
- **There is a third copy** at `out/Debug/editor/*.slang` (a build-output directory, not tracked in source control) that nothing automatically syncs — confirmed via the 2026-07-18 refresh that it can silently drift independently of the root/`editor/` pair (found `out/Debug/editor/mesh.slang` several days stale and missing a whole struct field compared to the two source copies, from unrelated work earlier in that session; the exact same class of bug cost significant debugging time chasing a "why doesn't my shader change take effect" symptom when the real cause was this stale third copy still being the one actually loaded at runtime). After touching any `.slang` file, explicitly check `out/Debug/editor/<name>.slang` (and rebuild/relaunch the editor, which does refresh it) rather than assuming the root/`editor/` diff alone proves the running shader is current.
